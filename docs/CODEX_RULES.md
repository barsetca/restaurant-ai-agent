# CODEX_RULES — правила работы Codex

## Приоритеты
1. Новое явно подтвержденное пользователем решение; 2. `docs/DECISIONS.md`; 3. `docs/ORIGINAL_REQUIREMENTS.md`; 4. архитектурные документы; 5. текущий этап. При конфликте или изменении scope остановиться и запросить решение. Исходные DOCX доступны владельцу проекта в ChatGPT Sources, но не обязаны находиться в репозитории.

## Перед каждым заданием
- Прочитать `docs/CODEX_RULES.md`, `docs/DEVELOPMENT_STATUS.md`, `docs/ORIGINAL_REQUIREMENTS.md`, `docs/ARCHITECTURE.md`, `docs/DATABASE_ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/PROJECT_HANDOFF.md`.
- Проверить `git status`, существующие файлы, миграции, тесты и конфигурацию. Не удалять работу пользователя, не выполнять `git push` без разрешения.
- Делать только текущий milestone, без преждевременной реализации следующего.

## После каждого промпта
1. Обновить `docs/DEVELOPMENT_STATUS.md`: фактические результаты, команды и статусы PASS/FAIL/NOT RUN, ограничения, следующий шаг. Не выдавать план за реализацию.
2. Обновить `docs/PROJECT_HANDOFF.md` для нового чата; при изменении архитектуры/БД — соответствующие документы, а при новом решении — `docs/DECISIONS.md`.
3. Создать Markdown-отчет в `history/NNN_<milestone>_report.md` **после каждого промпта**, даже если код не изменился. Номер NNN последовательно увеличивать, не перезаписывать предыдущие отчеты. Язык отчета — русский, кроме имен API, файлов, библиотек, команд и технических терминов.
4. Если **содержимое проекта изменилось**, после обновления документов создать `history/NNN_<milestone>_snapshot.zip`. Номер архива совпадает с номером отчета. При отсутствии изменений ZIP не создавать и указать причину.
5. В ответе привести краткий отчет, ссылки на локальные пути, список измененных файлов и результаты проверок.

## Правила безопасного ZIP
- Архивировать проект из корня с относительными путями; включать исходники, конфигурационные шаблоны, документацию, миграции и тесты.
- Исключать: `history/`, `.git/`, `.env`, `.env.*` (кроме `.env.example`), `*credentials*.json`, `*service-account*.json`, `*secret*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.sqlite*`, `__pycache__/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.venv/`, `venv/`, `node_modules/`, `*.log`, `*.zip`, временные файлы и дампы БД.
- Проверить имена файлов и содержимое на токены, API keys, пароли, реальные контакты и адреса; при сомнении не включать файл, сообщить о причине. **Не заменять секреты внутри рабочего файла ради архива**.
- Использовать allowlist на основе `git ls-files` плюс новые необходимые файлы после проверки; не полагаться только на `.gitignore`. Архив может включать незакоммиченные файлы проекта, но не секреты.
- Проверить `zipfile.testzip()` и список содержимого; указать размер архива. ZIP не отправлять в Git и не загружать автоматически в облако.

## Качество и безопасность
- Не логировать персональные данные, не публиковать секреты, использовать синтетические тестовые данные.
- Изменения схемы БД — только через Alembic; не удалять таблицы/данные без отдельного согласования.
- Писать минимальный поддерживаемый код, тестировать измененное, указывать реальные команды и результаты.
- Не менять согласованный scope молча. Не добавлять GitHub Actions, Kubernetes, n8n, Langfuse или второго LLM-провайдера.
