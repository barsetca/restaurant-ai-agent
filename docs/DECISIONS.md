# Architecture Decision Log

## ADR-001 — Один backend + отдельный MCP process
**Дата:** 2026-11-17. **Статус:** принято. FastAPI + Telegram + LangGraph в одном приложении; локальный Python MCP SDK server через stdio. Нет платформы микросервисов.

## ADR-002 — Разделение Google Sheets и PostgreSQL
**Дата:** 2026-11-17. **Статус:** принято. Google Sheets с вкладками `FAQ`, `Menu`, `Settings` — интерфейс редактирования; PostgreSQL — runtime source of truth для меню/настроек/заказов; Qdrant — FAQ index. Sync из admin UI без перезапуска, с валидацией и сохранением предыдущих корректных значений при ошибке.

## ADR-003 — Деньги и доставка
**Дата:** 2026-11-17. **Статус:** принято. EUR, integer minor units, редактируемая `delivery_fee_minor` в Settings; в заказе сохраняется снимок доставки и цен. При изменении итога требуется повторное подтверждение.

## ADR-004 — Подтверждение и Calendar
**Дата:** 2026-11-17. **Статус:** принято. Никаких побочных эффектов до явного подтверждения; уникальный `confirmation_key`; `calendar_jobs` для retry и идемпотентности; при ошибке `calendar_pending`.

## ADR-005 — Локальная разработка и документы
**Дата:** 2026-11-17. **Статус:** принято. Telegram long polling; документация `docs/` в Git, отчеты/ZIP в игнорируемом `history/`; два исходных DOCX остаются отдельно в Sources ChatGPT.

## ADR-006 — Учебные ограничения
**Дата:** 2026-11-17. **Статус:** принято. 10 дней, один вымышленный ресторан, русский интерфейс, синтетические данные, без реальных платежей, GitHub Actions, Kubernetes, n8n и второго LLM-провайдера.

## ADR-007 — Представление ingredients и allergens
**Дата:** 2026-11-17. **Статус:** принято для MVP. Поля `menu_items.ingredients` и `menu_items.allergens` хранятся как PostgreSQL `TEXT[] NOT NULL`. Это сохраняет типизированный плоский список и не вводит неограниченную JSON-схему; более сложная нормализация отдельными таблицами не нужна для одного демонстрационного ресторана. Sync service позднее отвечает за очистку и нормализацию элементов.

## ADR-008 — Идентичность блюд при синхронизации Menu
**Дата:** 2026-11-17. **Статус:** принято для будущего sync milestone. Google Sheets `Menu` остается редактируемым источником, а PostgreSQL `menu_items` — runtime source of truth. Sync выполняет upsert по стабильному `source_row_id`, сохраняя существующий `menu_items.id`. Блюда, отсутствующие в очередном корректном наборе источника, физически не удаляются, а получают `available=false`. Исторические `order_items` независимо сохраняют `name_snapshot`, `unit_price_minor` и `line_total_minor`. Реализация sync в M1.1 не входит.

## ADR-009 — Идемпотентный FAQ index и состояние sync
**Дата:** 2026-11-17. **Статус:** принято для M2. `FAQ` в Google Sheets — редактируемый источник FAQ, Qdrant collection `faq` — runtime searchable index. Стабильный `source_id` преобразуется в UUID5 point ID; `content_hash` хранится в payload и позволяет не вызывать embeddings для неизмененных записей. Измененные записи upsert-ятся, отсутствующие/неактивные удаляются только после успешных embeddings и upsert. Повторный запуск восстанавливает частично обновленный индекс. Таблица PostgreSQL `faq_sync` в M2 не используется, чтобы не создавать второй независимый источник состояния; она зарезервирована для будущего audit/job metadata.

## ADR-010 — Совместимость embedding collection
**Дата:** 2026-11-17. **Статус:** принято для M2. Qdrant collection хранит служебную metadata point с именем embedding model и размерностью. Несовпадение размерности или модели приводит к явной ошибке; молчаливое смешивание несовместимых vectors запрещено. Плановая смена модели требует новой collection либо отдельной контролируемой полной переиндексации.

## ADR-011 — Grounded FAQ answer и safe fallback
**Дата:** 2026-11-17. **Статус:** принято для M2. Similarity threshold лишь отбирает кандидатов и не считается доказательством ответа. Ограниченный FAQ-контекст передается как недоверенные JSON-данные в `ChatOpenAI`; structured decision отдельно сообщает `supported` и `conflicting`. Пустой, недостаточный, противоречивый контекст либо ошибка Sheets/OpenAI/Qdrant/Telegram приводит к фиксированному fallback без технических деталей. Исходный текст сообщения и exception details не логируются.

**Уточнение 2026-11-18 для M5:** если найденный FAQ-контекст надежно относится к теме вопроса, но сам вопрос допускает несколько смыслов, structured decision может вернуть `clarification_needed` и один короткий уточняющий вопрос без фактов. Это не снижает retrieval threshold и не разрешает отвечать содержанием, которого нет в context. При отсутствии надежного context, конфликте, ошибке или пустом clarification сохраняется фиксированный fallback.

## ADR-012 — Защита FAQ index от пустого источника
**Дата:** 2026-11-17. **Статус:** принято для M2.1. Если источник возвращает ноль active FAQ при наличии FAQ points в Qdrant, sync по умолчанию завершается `EmptyFaqSourceError` до удаления. Намеренная полная очистка требует явного CLI-флага `--allow-empty-source`; metadata point не входит в список FAQ hashes и сохраняется. Это защищает от пустой/ошибочной Sheet, не вводя distributed transaction.

## ADR-013 — Live-калибровка FAQ retrieval threshold
**Дата:** 2026-11-17. **Статус:** принято для текущего synthetic dataset. Threshold `0.72` отклонял известный вопрос (top score `0.5748`) и перефразированный вопрос (`0.3581`). Unknown question имел максимум `0.2555`. Значение `0.30` пропускает known/paraphrased context, отсекает согласованный unknown case, после чего structured answer check сохраняет fallback. Threshold необходимо переоценивать при смене FAQ dataset или embedding model; это не универсальная константа качества.

## ADR-014 — Централизованная санитизация логов
**Дата:** 2026-11-17. **Статус:** принято для M2.3. Все Python `LogRecord` проходят redaction до handlers: обрабатываются `msg`, parameterized `args`, object-valued args (включая `httpx.URL`) и предварительно форматированный `exc_info`. JSON formatter выполняет второй redaction поздних `extra` fields. Маскируются Telegram token, OpenAI key, Authorization/Bearer/API-key headers, URL passwords, private-key blocks и runtime secrets, переданные из Settings. Сторонние логгеры не отключаются. Telegram HTTP timing записывается отдельным безопасным record с method, endpoint без token, status и duration; message payload/chat data не логируются.

## ADR-015 — M3.1 deterministic routing и ephemeral graph state
**Дата:** 2026-11-17. **Статус:** принято для M3.1. Один compiled `StateGraph` становится основной точкой обработки Telegram text messages. Router не вызывает LLM: только явные action-patterns заказа ведут в `order`, пустые/некорректные сообщения — в `unknown`, остальные и неоднозначные — в `faq`. FAQ node переиспользует `FaqAssistant`; order node не имеет side effects и возвращает placeholder. State состоит только из сериализируемых примитивов: message, intent, response, safe error code и pseudonymous conversation ID. Checkpointer отсутствует; `MemorySaver`/`InMemorySaver`, custom serialization и ложная persistence запрещены. PostgreSQL checkpoint определяется отдельным будущим решением.

## ADR-016 — Official PostgreSQL saver и schema ownership
**Дата:** 2026-11-17. **Статус:** принято для M3.2. Persistence реализуется только `langgraph-checkpoint-postgres==3.2.1` через `AsyncPostgresSaver` и managed Psycopg async pool; SQLAlchemy/asyncpg не подменяется. Official tables `checkpoint_migrations`, `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` принадлежат saver и не включаются в Alembic/ORM приложения. `setup()` запускается явной operator-командой под PostgreSQL advisory lock, не на backend startup. Startup и readiness fail closed при обязательном, но недоступном saver; in-memory fallback запрещён. Serializer разрешает только безопасные primitive state values и не импортирует произвольные msgpack modules.

## ADR-017 — Versioned HMAC thread identity
**Дата:** 2026-11-17. **Статус:** принято для M3.2. Telegram chat ID преобразуется в `telegram:<key_id>:<HMAC-SHA256>` с отдельным `THREAD_ID_HMAC_SECRET` длиной не менее 32 символов. Telegram token не используется как HMAC key. Secret обязателен только при `TELEGRAM_ENABLED=true`, попадает в runtime log redactor и не хранится в Git/checkpoint. Смена key/`THREAD_ID_HMAC_KEY_ID` начинает новый namespace; автоматической миграции старых диалогов нет, поскольку до M3.2 persistent checkpoints отсутствовали. Ротация после появления production state требует отдельного migration/dual-read решения.

## ADR-018 — Сериализация сообщений одного thread
**Дата:** 2026-11-17. **Статус:** принято для текущего single-instance Telegram deployment. `AgentService` использует слабый registry per-thread async locks: сообщения одного `thread_id` выполняются последовательно, разные thread не блокируют друг друга. Это предотвращает lost updates `turn_count` внутри единственного backend process. Глобальная user-processing lock не вводится. Несколько backend/polling instances не поддерживаются; перед горизонтальным масштабированием потребуется distributed per-thread coordination или другой официальный concurrency control.

## ADR-019 — Explicit dietary tags и read-only MCP menu boundary
**Дата:** 2026-11-18. **Статус:** принято для M4. `menu_items.dietary_tags` хранится как `TEXT[] NOT NULL DEFAULT '{}'` и добавляется отдельной Alembic migration `0002`; исходная M1 migration не изменяется. Теги являются только явными source данными и никогда не выводятся из отсутствия ingredients/allergens. Будущий Google Sheets Menu sync добавит это поле в M7. MCP реализован отдельным Python MCP SDK v2 stdio process; backend использует typed client adapter. Tools работают в transaction-level read-only PostgreSQL sessions, возвращают structured output, ограничивают размеры входа и вычисляют только EUR subtotal в integer minor units без delivery. M4 не подключает MCP к LangGraph, не создаёт persistent cart/orders/Calendar и не меняет M3.2 workflow.

## ADR-020 — Явный owned DEV menu seed
**Дата:** 2026-11-18. **Статус:** принято как подготовка development data к M5 без начала M5. Synthetic menu загружается только явной operator-командой `python -m scripts.seed_menu`, не через Alembic и не при backend startup. Ровно 15 записей имеют stable UUID5 и `dev-menu-*` source IDs. Atomic upsert обновляет только заранее объявленные UUID/source pairs; предварительная ownership-проверка и PostgreSQL transaction advisory lock предотвращают перезапись конфликтующих или concurrent данных. Команда не удаляет произвольные строки, не выводит DSN и не заменяет будущий Google Sheets Menu sync M7.

## ADR-021 — Hybrid M5 intent boundary, checkpoint draft и явное подтверждение
**Дата:** 2026-11-18. **Статус:** принято для M5. ADR-015 сохраняется для deterministic guards, state transitions и бизнес-правил, но natural-language menu/cart intent разрешено извлекать OpenAI-моделью только в строгий `OrderIntentProposal` Pydantic contract. LLM не получает contact fields/full checkpoint, не изменяет cart, не выбирает ambiguous dish, не рассчитывает деньги и не подтверждает заказ. Dish resolution и availability выполняются через read-only MCP; cart bounds и mutations — pure deterministic code; subtotal — только `calculate_cart`; `delivery_fee_minor` — read-only key из `restaurant_settings`, без default/hardcode. M5 — delivery-only: validated name/phone/address обязательны, requested time optional (`None` = ASAP), explicit time хранится ISO 8601 `Europe/Madrid`. Cart/contact/quote/confirmed draft и bounded Telegram replay metadata хранятся в official PostgreSQL checkpoint; отдельная cart table не создаётся. Duplicate/out-of-order `update_id` не повторяет mutation; один backend instance остаётся обязательным. Confirmation допустим только после fresh quote и exact «Подтверждаю»; price/fee/revision change требует новой summary и повторного подтверждения. `confirmed_order` immutable, stable confirmation key повторно используется, а ответ явно сообщает, что заказ ещё не размещён. M5 не пишет `orders`/`order_items`/`calendar_jobs` и не выполняет Calendar/Sheets/payment side effects. Validated PII разрешена в checkpoint, очищается вместе с unconfirmed draft при cancel; confirmed snapshot сохраняется до M6. Retention/pruning остаётся открытым production-решением.

**Уточнение 2026-11-18 после manual E2E:** deterministic `new_order` архивирует текущий immutable snapshot и начинает пустой draft; FIFO-порядок сохраняется в `confirmed_order_archive`. В thread допускается максимум пять snapshots суммарно (`archive + confirmed_order`), после чего новый draft блокируется до отдельного решения об удалении. `/start` только описывает текущий state, `cancel` очищает лишь активный unconfirmed draft. Menu resolver использует исходную фразу и LLM canonical `lookup_query`, затем read-only MCP search с PostgreSQL Russian FTS; LLM не выбирает ID. Pending multi-item batch применяется только после разрешения всех строк. Delivery time в M5 выбирается ASAP либо вводится строго как `ДД.ММ.ГГГГ ЧЧ:ММ` в `Europe/Madrid`; сложный natural-language time parser и calendar picker отложены.

**Уточнение 2026-11-18 после manual E2E round 2:** confirmation/edit/cancel Telegram callbacks проходят только через `AgentService` и existing LangGraph checkpoint, содержат action + draft revision без PII и до mutation проверяют current stage/revision. Summary предлагает confirm/edit/two-step cancel; реальное изменение cart/contact/time повышает revision, инвалидирует quote и требует fresh summary/confirmation. Text aliases confirmation stage детерминированы до LLM; «нет» означает edit только в этом stage. После failed exact/canonical/MCP/FTS lookup decrement/remove/set допускается strict bounded fuzzy comparison только по active cart; кандидат никогда не применяется без numbered user selection. Telegram delivery использует sanitized helper: один bounded retry только для chained pre-delivery `httpx.ConnectError`; read timeout и иные ambiguous outcomes не повторяются. Checkpoint-before-send/replay не меняются, confirmed snapshot не откатывается, durable outbox не вводится.

**Уточнение 2026-11-18 для M5.2-A1:** destructive `new_order`, `clear` и `cancel` из любого classifier source не могут уничтожить непустой active unconfirmed draft без отдельного revision-bound подтверждения. До callback checkpoint хранит optional typed pending action и return stage; cart, contacts, quote, revision и confirmed snapshots не меняются. Confirm выполняет existing mutation один раз через общий replay path, отказ восстанавливает прежнюю stage. Confirmed cart не считается active draft, поэтому уже подтвержденный snapshot штатно архивируется при начале следующего заказа. Однозначные phrases «Хочу оформить заказ» и «Покажи мой заказ» обрабатываются deterministic; однословное «Заказ» требует clarification. LLM architecture/history не меняются до M5.2-A2.

**Корректировка 2026-11-18 для M5.2-A1:** stage и `draft_revision` недостаточны для различения двух successive destructive confirmations без mutation. Каждый pending `new_order`/`clear`/`cancel` получает независимый 12-character URL-safe confirmation session ID; destructive callback содержит и обязан совпасть по action, stage, revision и session ID. Decline/confirm удаляет pending session, старый или legacy callback без ID fails safe. Изменять `draft_revision` только ради button invalidation запрещено. Ordinary text не подтверждает destructive action; только актуальный callback может выполнить mutation. Official checkpoint schema не меняется, потому что ID — optional JSON-safe state value.

**Уточнение 2026-11-19 для M5.2-A2.1:** natural-language extraction получает не full checkpoint, а typed allowlisted `OrderContext`: stage/expected input, cart counts, текущий LLM action allowlist, typed semantic history максимум 10 events, trusted public dish label и только facts/counts confirmed snapshots. Raw history, contacts, IDs, callback/session tokens, quote/snapshot bodies и replay responses исключены. LLM возвращает strict discriminated `action/clarify/unsupported`; callback-only/confirmation actions отсутствуют в LLM allowlist, а validated action через compatibility adapter остается только proposal для deterministic `OrderDialog`. Contact stages не вызывают contextual LLM; deterministic navigation/question guards выполняются до field validation. Obvious PII gate fail closed, но не считается абсолютной PII detection. Persistent multi-turn clarification/session остается A2.2; DB schema и callback protocol не меняются.

**Корректировка 2026-11-19 для M5.2-A2.1 Structured Outputs/recovery:** OpenAI boundary использует flat strict API DTO без unsupported domain constraints, затем обязательно повторно валидирует прежние domain outcomes. Если API DTO распарсен, но нарушает один из allowlisted исправимых fixed rules (missing items, single-item count, missing set quantity, missing search selector), extractor может выполнить ровно один repair call с тем же safe `OrderContext` и исходным message плюс только rule code; invalid payload не повторяется. API/network/schema parse errors, bounds и прочие нарушения не retry. Второй failure всегда fail closed. До valid outcome нет dialog/MCP/cart side effects; replay guard не меняется.

**Корректировка 2026-11-19 для M5.2-A2.1 DTO normalization/debug:** transport DTO не обязан идеально обнулять необязательные поля. Adapter выбирает только action-relevant payload: item actions сохраняют items и отбрасывают selectors; search/browse сохраняют selectors и отбрасывают items; parameterless actions отбрасывают оба набора. Action/kind/item contents/quantity не переписываются, missing mandatory values не подставляются, raw DTO до normalization проходит output PII gate. Лишние безвредные поля не вызывают retry; ambiguous variant fields fail closed. Optional full-structure DTO debug использует только redacted parsed JSON, max 4000 chars, default off и effective only для development/dev/local; production принудительно off.

## ADR-022 — Ordered multi-action cart plan и атомарная candidate cart
**Дата:** 2026-11-19. **Статус:** принято для M5.2-A2.2. OpenAI strict transport DTO сохраняет прежний `kind=action` для одиночных намерений и добавляет плоский `kind=actions` с обязательным ordered `operations`; discriminated union в API schema не используется. Multi-action ограничен максимум 8 операциями `add`, `set_quantity`, `decrement`, `remove`; каждый operation повторно проходит domain bounds, stage allowlist и PII checks. Все блюда разрешаются authoritative MCP/catalog mechanism до mutation. Неоднозначность хранит полный pending plan и выбранные server-side IDs, но cart не меняет. Cross-operation повтор одной resolved dish отклоняется как конфликт; повтор внутри одного `add` детерминированно агрегируется существующим cart helper. После resolution операции применяются по порядку только к локальной candidate cart, а graph получает один итоговый cart update; unknown, ambiguity, conflict или cart bound failure возвращает safe order clarification без FAQ fallback и без cart update. Telegram replay guard и A1 destructive confirmations не меняются. При failure финального official checkpoint LangGraph pending-write semantics могут восстановить старый state либо весь terminal batch; частичного per-operation cart нет. Обязательный rollback к старому state при любой saver error потребовал бы отдельного изменения transaction architecture и в A2.2 не вводится.

**Корректировка 2026-11-19 для quantity validation:** transport DTO намеренно не содержит numeric schema constraints, поэтому hard bounds проверяются backend adapter до создания domain `ProposedItem`. Явное quantity выше `MAX_ITEM_QUANTITY=20` преобразуется в typed `ValidationOutcome(quantity_out_of_range)` после raw-output PII gate и без LLM retry. Compatibility adapter создает order clarification с фиксированным текстом и не передает plan в mutation dialog; single и multi requests используют один путь. Quantity 20 остается валидным, domain `ge/le` validators не ослабляются. Значения ниже minimum и любые другие `ValidationError` не маскируются этим outcome и сохраняют общий fail-closed путь.

## ADR-023 — Bounded semantic continuation и authoritative dish referent
**Дата:** 2026-11-19. **Статус:** принято для M5.2-A2.3. Semantic clarification хранится только как optional typed JSON-safe checkpoint value: fixed reason, server-side allowlisted choices, return stage и independent 12-character session ID. Callback использует существующий revision/session envelope и общий replay path; LLM при pending получает только narrowed action allowlist и не может создавать произвольные операции. A1 destructive barrier имеет приоритет, topic switch/cancel/new order инвалидируют semantic pending. Existing numbered dish disambiguation остается отдельным mechanism и не дублируется. Backend-only `last_referenced_dish_id` устанавливается лишь после authoritative catalog resolution; LLM получает только public dish label, а details/allergens всегда перечитываются через `get_dish`. Previous-order ответы ограничены current/archive confirmed checkpoint facts и обязаны отличать snapshot от отсутствующего до M6 business order/status. DB schema, MCP contracts и model не меняются.

## ADR-024 — Deterministic checkout и полная LLM-изоляция contact input
**Обновление статуса 2026-11-19:** IMPLEMENTED / AUTOMATED TARGETED PASS / LIVE ACCEPTANCE PENDING. Реализованы early contact gate, empty LLM allowlist, deterministic Unicode validators, одноразовое checkout notice, callback-only cancel и independent checkout session validation. Retention/удаление PII из исторических checkpoint versions остается отдельной отложенной privacy-задачей.

**Дата:** 2026-11-19. **Статус:** принято владельцем / IMPLEMENTED, LIVE ACCEPTANCE PENDING. После входа в `collecting_name`, `collecting_phone`, `collecting_address`, `collecting_time` и соответствующие `collecting_edit_*` стадии любой обычный text update интерпретируется только как значение ожидаемого поля и не передается contextual extractor, FAQ embeddings/answerer или другому LLM path. Исключения разрешены только через allowlisted Telegram callbacks. Прежние требования отвечать на FAQ/выполнять text navigation во время contact collection из `M5_2_DESIGN_HANDOFF.md`, ADR-021/A2.1 и старых tests этим решением superseded. Отмена checkout — отдельный callback-only action: сохраняет cart, очищает весь unconfirmed `contacts`/quote, возвращает `order_stage=idle` и не запускает A1 cancel, confirmation или placement. Для защиты от старой кнопки используется optional checkpointed checkout session token; существующий четырехчастный callback envelope и replay guard переиспользованы без DB schema change. Формальная deterministic name validation не доказывает, что строка семантически является именем: syntactically valid фраза может быть принята и должна быть проверена пользователем в summary. Contacts и checkpoint responses остаются разрешенным state storage, но ни full state, ни replay/response/contact values не передаются LLM; checkpoint retention/pruning остается отдельным production решением.
